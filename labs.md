## Наскрізні умови курсу

Оголошуються на першому занятті й діють для всіх робіт.

- **Усі репозиторії курсу — публічні.** На безкоштовному плані GitHub правила захисту гілок, обов'язкові рецензенти й CODEOWNERS працюють лише в публічних репозиторіях, а хвилини CI для них не тарифікуються.
- **Курс наскрізний.** Застосунок із Лаб. 4 супроводжує студента до фінального проєкту. Кожна наступна робота нарощує той самий проєкт.
- **Стек фіксований для всієї групи:** основний API на FastAPI, допоміжний сервіс на Node.js, фронтенд на Vue, PostgreSQL, Redis. Вибору немає — це прибирає розбіжності в роботах 5–10.
- **Застосунок видається готовим стартовим репозиторієм.** Написання коду застосунку не входить у відповідальність курсу: оцінюються інженерні практики навколо коду.
- **Кожна робота здається через pull request** із власної гілки. Прямий пуш у `main` — незарахована робота незалежно від вмісту.
- **Усі платформи мають безкоштовний рівень без прив'язки платіжної картки.** Сервіс, що вимагає картку, у курсі не використовується.

# МОДУЛЬ 1: ОСНОВИ DEVOPS ТА АВТОМАТИЗАЦІЯ

## Лабораторна робота 1: Середовище та професійний Git workflow

**8 годин · 6 балів** (+2 бонусні)

**Мета:** підготувати робоче середовище і налаштувати репозиторій за правилами, які застосовують у командній розробці.

### Завдання 1. Налаштування Git (1 год)

Встановити Git і задати глобальні параметри:

- `user.name` і `user.email` — пошта має збігатися з підтвердженою поштою GitHub-акаунта, інакше коміти не прив'яжуться до профілю
- `init.defaultBranch=main`
- `core.autocrlf` — значення залежить від ОС; у звіті пояснити, чому воно різне для Windows і Unix і що станеться без нього в команді зі змішаними системами
- `pull.rebase=true` — пояснити, чим отримана історія відрізняється від типової
- редактор за замовчуванням для повідомлень комітів

**Перевірка:** вивід `git config --list --global` у звіті.

### Завдання 2. Редактор (1 год)

Налаштувати VS Code (або інший редактор — JetBrains, Neovim) для роботи з інфраструктурним кодом. Встановити розширення для:

- історії змін і авторства рядків у редакторі (GitLens або аналог)
- підсвічування та перевірки Dockerfile і Compose-файлів
- YAML із підключеною перевіркою за схемою — має підсвічувати помилку в конфігурації GitHub Actions **до** коміту
- перегляду Markdown

Створити `.editorconfig` із правилами відступів, кінців рядків і фінального переносу. Увімкнути форматування при збереженні.

**Перевірка:** скріншот, де редактор підсвічує навмисно зламаний YAML.

### Завдання 3. Середовища виконання (1 год)

- **Node.js** актуальної LTS-версії (на вересень 2026 — 24.x), встановлений **через менеджер версій** (nvm, fnm або volta), а не системним пакетом. Показати перемикання між двома версіями і пояснити, навіщо це потрібно, коли проєктів більше одного.
- **Python** актуальної стабільної версії (на вересень 2026 — 3.14), теж через менеджер версій або `uv`.
- **Середовище контейнеризації** на вибір: Docker Desktop, Podman Desktop, Rancher Desktop або colima. Обов'язково Compose v2 — перевірити `docker compose version` (з пробілом, не через дефіс).

**Перевірка:** вивід версій усіх інструментів.

### Завдання 4. GitHub і доступ (1 год)

- Акаунт із заповненим профілем: ім'я, фото, короткий опис. Профіль — частина портфоліо.
- Увімкнена двофакторна автентифікація.
- SSH-ключ типу `ed25519` із парольною фразою, публічна частина додана в акаунт.
- Перевірка з'єднання: `ssh -T git@github.com`, вивід у звіті.
- Письмово: чому приватний ключ ніколи не потрапляє в репозиторій і що робити, якщо він усе ж туди потрапив.

### Завдання 5. Портфоліо-репозиторій (2 год)

Створити **публічний** репозиторій `devops-portfolio`.

README має містити: коротке представлення, професійну мету в DevOps, перелік технологій із поділом на «вже знаю» і «планую вивчити», план розвитку на рік, контакти й посилання на профілі.

Додати:

- `.gitignore`, згенерований під використовувані технології, а не написаний вручну
- ліцензію
- структуру папок `lab-01` … `lab-10` і `docs/`

### Завдання 6. Правила репозиторію (1,5 год)

Створити `.github/CODEOWNERS` із власником на весь репозиторій та окремими власниками на `docs/` і `.github/`.

Ruleset для `main`:

- обов'язковий pull request перед злиттям
- обов'язкова рецензія від власників коду
- обов'язкове проходження перевірок статусу (додасться в Лаб. 4)
- заборона force-push і видалення гілки

Ruleset для `develop`: два обов'язкові схвалення, скидання застарілих рецензій при нових комітах.

У `docs/` письмово пояснити: чому в персональному репозиторії **не** вмикається заборона обходу правил адміністратором (інакше студент заблокує сам себе — автор PR не може його схвалити) і що зміниться в командному репозиторії Лаб. 2.

### Завдання 7. Дошка проєкту і шаблон PR (0,5 год)

Project із колонками Backlog / In Progress / Review / Done. Задача на кожен модуль курсу і на фінальний проєкт. Увімкнені вбудовані автоматизації: нова задача → Backlog, відкритий PR → Review, злитий PR → Done, закрита задача → Done.

`.github/pull_request_template.md`: опис змін, посилання на задачу, чек-лист самоперевірки, спосіб перевірки результату.

### Оцінювання

| Критерій | Бали |
|---|---|
| Git і редактор налаштовані, виводи перевірок наведено | 1 |
| Середовища через менеджер версій, Compose v2 | 1 |
| README, структура, `.gitignore`, ліцензія | 1 |
| CODEOWNERS і два ruleset із письмовим обґрунтуванням | 2 |
| Дошка з автоматизаціями, шаблон PR, робота здана через PR | 1 |

**Бонус (+2): правила як код.** Відтворити всі налаштування репозиторію не через веб-інтерфейс, а програмно — через API або консольний клієнт, зі збереженням конфігурації в репозиторії. Показати застосування до нового порожнього репозиторію однією командою.

## Лабораторна робота 2: Командна робота з Git

**6 годин · 5 балів** (+1 бонусний)

**Мета:** відпрацювати командний workflow, рецензування і вирішення конфліктів.

### Завдання 1. Команда і репозиторій (1 год)

Команди по 3–4 студенти. Один учасник створює публічний репозиторій `team-devops-handbook`, решта додаються як collaborators.

Ruleset для `main`:

- два обов'язкові схвалення
- скидання застарілих рецензій при нових комітах
- заборона force-push
- увімкнена заборона обходу правил адміністратором — на відміну від Лаб. 1, тут це коректно, бо в команді завжди є ще хтось, хто схвалить

**Перевірка:** скріншот налаштувань і список учасників у README.

### Завдання 2. Спільний артефакт (2 год)

Команда веде технічний довідник — це і є предмет роботи. Застосунок не пишеться.

Розділи в `docs/`, по одному відповідальному на розділ:

- конвенції іменування гілок і повідомлень комітів
- спільний `.editorconfig` і `.gitignore` для проєктів курсу
- шаблон README для нового проєкту
- чек-лист проведення code review

### Завдання 3. Процес pull request (1 год)

Кожен учасник працює у гілці `feature/<ім'я>-<тема>`. На кожну зміну — PR.

Вимоги до рецензії: щонайменше одне змістовне зауваження по суті, а не формальне схвалення. Автор вносить правки **окремим комітом** у ту саму гілку, не переписуючи історію поверх уже прорецензованого.

**Перевірка:** посилання на 3–4 злиті PR із видимими коментарями рецензентів.

## Лабораторна робота 3: Власний DevOps-інструментарій

**9 годин · 8 балів** (+2 бонусні)

**Мета:** написати інструменти автоматизації, які використовуватимуться далі в курсі.

**Спільні вимоги до всіх інструментів:** довідка за `--help`, ненульовий код виходу при помилці, перевірка вхідних параметрів, README з прикладами запуску. Для bash — `set -euo pipefail` і пояснення, що дає кожен прапорець.

### Завдання 1. Скрипт резервного копіювання (2 год)

Параметри: джерело, призначення, кількість копій для зберігання, режим без запису змін.

Функціонал: архівування зі стисненням, часова мітка в імені архіву, видалення копій понад задану кількість, журналювання кожного запуску з рівнями повідомлень, перевірка наявності джерела й вільного місця.

**Перевірка:** запуск шість разів поспіль із межею у п'ять копій — показати, що зайва видалилася.

### Завдання 2. Скрипт моніторингу системи (1,5 год)

Показники: використання процесора, пам'яті, дискового простору; стан заданих сервісів або процесів.

Пороги задаються змінними середовища або конфігураційним файлом, не хардкодяться. При перевищенні — повідомлення в журнал і ненульовий код виходу. Вивід придатний для запуску за розкладом.

**Перевірка:** штучно занизити поріг і показати спрацювання.

### Завдання 3. Аналізатор журналів веб-сервера (2 год)

Розбір комбінованого формату журналу. Результати: топ-10 адрес за кількістю запитів, розподіл кодів відповіді, години пікового навантаження.

Параметри командного рядка: вхідний файл, вихідний файл, формат виводу (текст або структурований), кількість позицій у топі. Коректна обробка пошкоджених рядків — не падати, а рахувати їх окремо.

**Обов'язково:** щонайменше один автоматичний тест на функцію розбору рядка.

### Завдання 4. Монітор доступності API (2,5 год)

Список endpoint'ів із конфігураційного файлу. Для кожного: очікуваний код відповіді, тайм-аут, поріг часу відповіді.

Базовий функціонал: вимірювання часу відповіді, повторна спроба при мережевій помилці, збереження результатів у структурованому форматі з часовою міткою, надсилання сповіщення у месенджер при невідповідності очікуванню.

**Розрізнення типів збою.** Монітор не має повідомляти «сервіс недоступний» на всі випадки життя. Кожен тип помилки обробляється окремо і потрапляє в журнал зі своїм повідомленням:

| Тип збою | Що це означає |
|---|---|
| Ім'я не резолвиться | Проблема з DNS — до сервісу навіть не намагалися достукатися |
| З'єднання відхилено | Сервер відповів, але на цьому порту ніхто не слухає |
| Тайм-аут з'єднання | Відповіді немає взагалі — імовірно, блокує мережевий екран |
| Помилка сертифіката | З'єднання є, сервіс живий, але клієнт відмовляється йому довіряти |
| HTTP-помилка | Сервіс відповів, але не тим кодом, якого очікували |

**Перевірка:** прогнати монітор по списку, що містить неіснуючий домен, закритий порт на доступному сервері, домен із простроченим сертифікатом (є публічні тестові домени саме для цього) і робочий endpoint, який повертає несподіваний код. У журналі мають бути чотири різні повідомлення, а не чотири однакові.

**Письмово в README:** чим «з'єднання відхилено» відрізняється від «тайм-аут» і чому в реальному інциденті ці два випадки ведуть до різних дій.

### Завдання 5. Інтеграція з Git (1 год)

Хук перед комітом — лінтер на змінені файли. Хук перед відправкою — запуск тестів.

Письмово: чому хуки не є засобом контролю (обходяться одним прапорцем) і чому обов'язкові перевірки в Лаб. 4 роблять те, чого хуки зробити не можуть.

## Лабораторна робота 4: Застосунок і безперервна інтеграція

**9 годин · 10 балів** (+2 бонусні)

**Мета:** розібратися в наданому застосунку і побудувати автоматичну перевірку якості коду.

### Завдання 1. Розбір кодової бази (1,5 год)

Клонувати стартовий репозиторій, підняти локально, переконатися, що всі компоненти відповідають.

Оформити `docs/architecture.md`: перелік компонентів із призначенням, порти, напрямок викликів між сервісами, схема (діаграма або текстовий опис).

### Завдання 2. Внесок у код (2,5 год)

Дописати по одному endpoint у кожен бекенд-сервіс:

- у FastAPI — з валідацією вхідних даних і коректним кодом відповіді при некоректному запиті
- у Node-сервісі — аналогічно

Покрити обидва тестами: позитивний сценарій і сценарій із некоректними даними. Обсяг коду свідомо малий — оцінюється не він, а те, що тести справді перевіряють поведінку.

### Завдання 3. Якість коду (2 год)

Для кожної мови підключити лінтер і форматер із конфігурацією в репозиторії. Налаштувати запуск тестів із вимірюванням покриття та мінімальним порогом (рекомендовано 60% на старті).

Команди запуску мають бути однаково названі для обох сервісів — це знадобиться в матриці.

### Завдання 4. Конвеєр інтеграції (3 год)

Workflow, що запускається на push і на pull request:

- **матрична стратегія** по двох сервісах замість двох скопійованих завдань
- **кешування** залежностей за файлом блокування версій
- **фільтри за шляхами** — зміна в одному сервісі не запускає збірку іншого
- **перевірка залежностей** на відомі вразливості для обох мов

Використовувати актуальні мажорні версії дій (на вересень 2026 — щонайменше `checkout@v5` і `setup-node@v6`); версії 4 і нижче не приймаються.

**Письмово:** чому матриця краща за два скопійовані завдання і що саме дають фільтри за шляхами.

### Завдання 5. Замикання на Лаб. 1 (1 год)

Підключити перевірки конвеєра як обов'язкові в ruleset основної гілки. Додати індикатор стану збірки в README.

**Перевірка:** відкрити PR із завідомо зламаним тестом і показати, що кнопка злиття заблокована.

## Лабораторна робота 5: Контейнеризація

**10 годин · 9 балів** (+2 бонусні)

**Мета:** зібрати образи обох бекенд-сервісів і підготувати локальне середовище розробки.

### Завдання 1. Образ Python-сервісу (2 год)

Багатоетапна збірка: окремий етап встановлення залежностей, окремий — фінальний образ. Непривілейований користувач. Перевірка стану контейнера. Файл виключень контексту збірки.

Базовий образ зафіксований конкретним тегом — не `latest`. Пояснити письмово, чим небезпечний `latest` у базовому образі.

### Завдання 2. Образ Node-сервісу (1,5 год)

Ті самі вимоги. Встановлення лише виробничих залежностей у фінальному образі.

### Завдання 3. Вимірювання оптимізації (1 год)

Таблиця: розмір кожного образу до і після застосування багатоетапної збірки. Пояснити, чому величина виграшу для двох мов різна.

### Завдання 4. Локальне середовище розробки (2,5 год)

Опис усіх сервісів: два бекенди, фронтенд, БД, кеш.

- запуск бекендів лише після готовності залежностей — за перевіркою стану, а не за фактом старту контейнера
- окремий режим розробки з гарячим перезавантаженням і монтуванням коду
- змінні середовища у файлах, не в описі сервісів
- іменовані томи під дані БД і кешу
- **окремий том під директорію залежностей** у сервісах із монтуванням коду

Ключ `version` не використовується — він застарілий.

**Письмово:** що станеться без окремого тому під залежності і чому проблема проявляється лише на частині машин.

### Завдання 5. Публікація з конвеєра (2 год)

Автоматична збірка й публікація обох образів у реєстр контейнерів при злитті в основну гілку.

Схема тегів: незмінний тег за ідентифікатором коміту, рухомий тег основної гілки, тег версії при створенні мітки. Пояснити, який тег використовувати в продакшені й чому.

### Завдання 6. Сканування і кешування шарів (1 год)

Сканування опублікованих образів на вразливості з наведеним результатом. Впорядкування інструкцій у Dockerfile так, щоб зміна коду не інвалідувала шар із залежностями — показати час повторної збірки до і після.

# МОДУЛЬ 3: МОНІТОРИНГ ТА БЕЗПЕКА

Стан і навантаження БД, співвідношення влучань і промахів кешу, показники інфраструктури або вузлів кластера.

### Завдання 4. Дашборди (2 год)

Панель на кожен сервіс і зведена панель загального стану системи, придатна для одного погляду: працює / не працює / деградує.

Вимога до зведеної панелі: людина без контексту має за п'ять секунд зрозуміти, чи все гаразд.

### Завдання 5. Алерти й інструкція реагування (1,5 год)

Правила: недоступність сервісу, зростання частки помилок понад поріг, вичерпання ресурсів. Доставка сповіщень у месенджер.

Для одного алерту написати `docs/runbook.md`: що саме означає спрацювання, що перевірити першим, які дії виконати, коли ескалувати.

### Завдання 6. Демонстрація збою (1 год)

Штучно вивести сервіс з ладу і показати повний ланцюжок: зміна на графіку → спрацювання правила → отримане сповіщення → відновлення → повернення метрики в норму.

Навести час від початку збою до отримання сповіщення.

### Оцінювання

| Критерій | Бали |
|---|---|
| Стек розгорнуто, виявлення цілей налаштоване | 2 |
| Метрики застосунку з поясненням перцентилів | 2 |
| Метрики БД, кешу та інфраструктури | 2 |
| Дашборди, зокрема зведена панель | 1 |
| Алерти та інструкція реагування | 2 |
| Демонстрація збою з виміряним часом реакції | 1 |

**Бонус (+3): журнали і трасування.** Централізований збір журналів і наскрізне трасування запиту через обидва бекенд-сервіси. Показати на одному запиті зв'язок метрики, запису в журналі й траси.

## Лабораторна робота 10: Практики DevSecOps

**10 годин · 9 балів** (+2 бонусні)

**Мета:** вбудувати перевірки безпеки в конвеєр так, щоб вони блокували небезпечні зміни.

**Обмеження:** будь-яке сканування проводиться виключно проти власних ресурсів студента. Сканування чужих систем — підстава для незарахування роботи.

### Завдання 1. Статичний аналіз (2,5 год)

Підключити хмарний сервіс аналізу коду до репозиторію — він дає аналіз pull request на безкоштовному рівні, на відміну від самостійно розгорнутої безкоштовної збірки.

Налаштувати аналіз на кожен PR і поріг якості як обов'язкову перевірку злиття. Виправити знайдені проблеми, навести стан до і після.

### Завдання 2. Безпека контейнерів (2,5 год)

Сканування обох образів у конвеєрі з блокуванням збірки при критичних вразливостях. Перехід на мінімальні базові образи.

Таблиця: кількість знахідок за рівнями критичності до і після переходу, для обох сервісів.

**Перевірка:** відкрити PR, що додає завідомо вразливу залежність, і показати заблоковану збірку.

### Завдання 3. Управління секретами (2,5 год)

Винести всі секрети з коду й файлів середовища у сховище секретів конвеєра. Просканувати **всю історію** репозиторію на витоки — не лише поточний стан.

`docs/secrets.md`: перелік усіх секретів проєкту з місцем зберігання і процедурою ротації скомпрометованого секрету. Окремо пояснити, чому видалення секрету останнім комітом не вирішує проблему.

### Завдання 4. Динамічний аналіз і залежності (1,5 год)

Просканувати власний розгорнутий застосунок інструментом динамічного аналізу. Проаналізувати залежності обох сервісів на відомі вразливості. Класифікувати знахідки: що виправляємо зараз, що приймаємо з обґрунтуванням.

### Завдання 5. Чек-лист безпеки (1 год)

`docs/security-checklist.md` — перевірки, які проходить проєкт перед випуском, із зазначенням, які з них автоматизовані, а які виконуються вручну.

### Оцінювання

| Критерій | Бали |
|---|---|
| Статичний аналіз і поріг якості на PR | 2 |
| Сканування образів із блокуванням і таблицею знахідок | 2 |
| Секрети винесені, історія перевірена, процедура ротації | 2 |
| Динамічний аналіз і класифікація знахідок | 2 |
| Чек-лист безпеки | 1 |

**Бонус (+2): політики як код.** Автоматична перевірка описів інфраструктури й маніфестів кластера на відповідність правилам безпеки з блокуванням злиття. Навести приклад порушення, яке перевірка спіймала.

# ФІНАЛЬНИЙ ПРОЄКТ

## Комплексний DevOps Lifecycle

**8 годин · 16 балів** (+1 бонусний)

**Мета:** звести напрацювання лабораторних 4–10 в один зв'язний проєкт і захистити його.

**Формат.** Нового коду й нової інфраструктури створювати не потрібно. Робота полягає у зведенні, узгодженні, документуванні та демонстрації вже зробленого.

### Завдання 1. Зведення (3 год)

Привести все до працездатного стану одночасно: конвеєр проходить, застосунок розгорнутий і доступний, моніторинг збирає метрики, перевірки безпеки активні.

Студент обирає, який варіант розгортання захищає — керовану платформу з Лаб. 6 чи кластер із Лаб. 7 — і обґрунтовує вибір.

### Завдання 2. Документація (3 год)

- схема архітектури з усіма компонентами й потоками
- README з інструкцією запуску з нуля: людина без контексту має відтворити середовище за цим текстом
- `docs/decisions/` — записи про прийняті рішення щонайменше по трьох розвилках курсу: контекст, розглянуті варіанти, вибір, наслідки
- інструкція реагування на один інцидент

### Завдання 3. Підготовка демонстрації (1,5 год)

Відпрацювати наскрізний сценарій: зміна в коді → проходження конвеєра → розгортання → відображення на дашборді моніторингу. Заміряти час проходження, підготувати запасний варіант на випадок збою мережі під час захисту.

### Завдання 4. Презентація (0,5 год + захист)

Десять хвилин: коротко про архітектуру, жива демонстрація наскрізного сценарію, висновки — що виявилося складнішим за очікуване і що зробили б інакше.

### Оцінювання

| Критерій | Бали |
|---|---|
| Цілісність і працездатність зібраного проєкту | 5 |
| Повнота процесів (CI/CD, IaC, оркестрація, моніторинг, безпека) | 4 |
| Документація, зокрема записи про рішення | 3 |
| Презентація і жива демонстрація | 2 |
| Відповіді на питання по проєкту | 2 |

**Бонус (+1): вартість володіння.** Оцінити утримання проєкту протягом року на платних тарифах використаних платформ і запропонувати одну зміну архітектури, що суттєво зменшує суму.
