# Лабораторна робота 7 — Оркестрація контейнерів

**9 балів** · бонусні завдання +6

## Мета

Перенести wishlist з Лаб. 6 у локальний кластер Kubernetes разом з базою й кешем. Описати
все маніфестами так, щоб кластер і застосунок піднімалися з нуля однією командою, а
оновлення, відкат і падіння окремих частин відбувалися передбачувано.

Робота не про те, щоб «поди стали Running», а про те, щоб розуміти, що робить кластер,
коли щось іде не так: падає под, зникає нода, закінчується пам'ять.

## Проєкт

Ті самі `wishlist-api` і `wishlist-ui`, ті самі образи в GHCR за sha-тегом з Лаб. 6.

Кластер — k3d (k3s у Docker) на власному комп'ютері, без хмарних провайдерів. Потрібні
Docker і приблизно 4 ГБ вільної пам'яті.

На відміну від Лаб. 6, Postgres і Redis працюють усередині кластера: мета — побачити, як
Kubernetes поводиться зі станом. Де лежать маніфести (окремий репозиторій чи каталог в
одному з наявних), вирішує команда.

> UI доступний на `http://wishlist.localhost:8080`, API — на
> `http://api.wishlist.localhost:8080`. Якщо ваша система не резолвить `*.localhost`,
> додайте записи в `/etc/hosts`.

## Завдання

### 1. Кластер як код (1 бал)

- Конфігурація k3d у файлі в репозиторії: один server, два agents, закріплена версія
  образу k3s, порт 8080 на вбудований load balancer.
- Одна команда (скрипт або `Makefile`) створює кластер і розгортає весь застосунок з
  нуля, друга — повністю його видаляє.
- Усі ресурси застосунку — в окремому namespace, а не в `default`.

**Доказ:** вивід `kubectl get nodes -o wide` і час від видалення кластера до робочого
застосунку.

### 2. Дані в кластері (2 бали)

- Postgres — StatefulSet з PersistentVolumeClaim і headless Service. Основна версія та
  сама, що в Лаб. 6.
- Redis — Deployment без постійного сховища: кеш можна втратити.
- Паролі — у Secret, якого немає в репозиторії. Як Secret потрапляє в кластер, опишіть у
  `K8S.md`.
- Видаліть под Postgres і покажіть, що після перезапуску дані на місці.
- Знайдіть, де фізично лежать дані Postgres: на якій ноді й у якому каталозі. Поясніть,
  що це означає, якщо под Postgres доведеться перенести на іншу ноду.
- Коротко: що з цього в реальному проєкті ви б лишили в кластері, а що винесли б у
  керовані сервіси, як у Лаб. 6, і чому.

<details>
<summary>Підказка</summary>

Подивіться на `kubectl get pv -o yaml` і на те, який StorageClass k3s використовує за
замовчуванням.

</details>

### 3. Застосунок у кластері (2 бали)

- api і ui — Deployment і Service. api — щонайменше у двох копіях.
- Образи з GHCR за sha-тегом. Якщо пакети приватні — через `imagePullSecret`.
- Конфігурація через ConfigMap і Secret, ті самі змінні, що в Лаб. 6. `ALLOWED_ORIGINS` —
  адреса UI в кластері.
- Ingress через вбудований Traefik, ui і api на своїх адресах. Оновлення сторінки на
  будь-якому маршруті застосунку не дає 404.
- Readiness- і liveness-проби для api. Вони не однакові: поясніть, що перевіряє кожна і
  чому.
- Requests і limits для всіх контейнерів, обґрунтовані заміряним споживанням
  (`kubectl top`), а не взяті зі стелі.
- Маніфести застосовуються однією командою `kubectl apply -k`.

У `K8S.md` опишіть, що довелося зробити, щоб варіант UI, обраний у Лаб. 6, запрацював у
третьому середовищі, і що це говорить про ваш вибір.

<details>
<summary>Підказка</summary>

Що станеться з усіма копіями api, якщо liveness-проба перевіряє базу, а база недоступна
одну хвилину?

</details>

**Доказ:** `kubectl get pods,svc,ingress -n <namespace>` і таблиця заміряного споживання
поруч із виставленими requests і limits.

### 4. Міграції (1 бал)

- Міграція — Job з тим самим образом api і командою `alembic upgrade head`.
- api оновлюється лише після успішної міграції. Якщо Job впав, старі копії api
  продовжують працювати.
- Як забезпечити цей порядок, вирішує команда: окремий крок у скрипті, initContainer або
  інший спосіб. У `K8S.md` назвіть недолік обраного способу, який ви свідомо прийняли.

<details>
<summary>Підказка</summary>

Job незмінний: повторний `apply` зміненого Job завершується помилкою. Подумайте про
імена Job для кожного sha і про `ttlSecondsAfterFinished`. Для порядку в скрипті
стане в пригоді `kubectl wait --for=condition=complete`. Якщо обираєте initContainer:
що буде, коли дві копії api стартують одночасно?

</details>

### 5. Перевірка в конвеєрі (1 бал)

Кластер на вашому комп'ютері недоступний з GitHub Actions, тож конвеєр не розгортає, а
перевіряє.

- На кожен pull request маніфести проходять валідацію, наприклад kubeconform.
- Конвеєр піднімає тимчасовий k3d-кластер у раннері, застосовує маніфести, чекає на
  успішне розгортання й через Ingress перевіряє `/health` і одну сторінку UI.
- Якщо перевірка не пройшла, pull request не можна злити.

<details>
<summary>Підказка</summary>

На раннерах GitHub Docker уже є, а k3d ставиться однією командою. Секрети для тимчасового
кластера — тестові значення або секрети GitHub, але не з репозиторію.

</details>

**Доказ:** запуск, що впав через навмисно зламаний маніфест, і запуск, що пройшов.

### 6. Експлуатаційні перевірки (2 бали)

Під час кожної перевірки в окремому терміналі в циклі йдуть запити до API. Фіксуйте,
скільки з них були неуспішними.

- **Оновлення.** Розгорніть новий sha api. Покажіть стратегію оновлення (`maxSurge`,
  `maxUnavailable`) і кількість невдалих запитів. Якщо їх не нуль, поясніть чому.
- **Відкат.** Виконайте `kubectl rollout undo` і покажіть, який образ працює після нього.
  Поясніть, що тепер не так з маніфестами в репозиторії і як це виправити.
- **Под.** Видаліть одну копію api.
- **Без кешу.** Зробіть Redis недоступним, наприклад масштабуйте до нуля. api лишається
  ready, поди не перезапускаються.
- **Нода.** Зупиніть agent-ноду, на якій працює Postgres. Зачекайте щонайменше 6 хвилин
  і опишіть, що сталося з подами api і з Postgres, і чому. Потім поверніть ноду.
- **Пам'ять.** Тимчасово поставте api ліміт пам'яті, менший за заміряне споживання.
  Покажіть, що сталося, і поверніть як було.

Усе — у `K8S.md`, з командами й цифрами.

<details>
<summary>Підказка</summary>

Запити в циклі:

```bash
while true; do
  curl -s -o /dev/null -w "%{http_code}\n" http://api.wishlist.localhost:8080/health
  sleep 0.1
done | tee codes.txt
```

Підсумок: `sort codes.txt | uniq -c`. Ноди k3d — це контейнери, тож зупинити ноду можна
через `docker stop`. Чому поди не переїжджають одразу, підкажуть `tolerations` будь-якого
пода.

</details>

## Бонусні завдання (+6)

- **GitOps (+2).** Argo CD у кластері стежить за репозиторієм з маніфестами. Після
  публікації образу конвеєр комітом оновлює sha в `kustomization.yaml`. Поясніть, чому
  модель, де кластер сам забирає зміни, підходить для кластера, недоступного з інтернету.
- **Оновлення без помилок (+1).** Під час оновлення під навантаженням немає жодного
  невдалого запиту завдяки коректному завершенню подів. Поясніть, звідки бралися помилки
  без нього.
- **NetworkPolicy (+1).** До Postgres і Redis можуть звертатися лише api і Job міграції.
  Доказ — невдала спроба підключитися з іншого пода.
- **Автомасштабування (+1).** HorizontalPodAutoscaler для api за CPU. Під навантаженням
  (hey, k6) кількість копій зростає, потім спадає. metrics-server у k3s уже є.
- **Обслуговування ноди (+1).** PodDisruptionBudget для api і `kubectl drain` ноди без
  жодного невдалого запиту.

## Спільні вимоги

- Закріплені версії образів, зокрема k3s, і actions. Жодного `latest`.
- Жодного секрету в репозиторії, образі чи логах конвеєра.
- Зрозумілі імена ресурсів і мітки (`app`, `component`).
- `K8S.md`: як підняти й видалити все, схема ресурсів, рішення й цифри із завдань 2, 3, 4
  і 6.
- На захисті кластер створюється з нуля однією командою, і застосунок працює.
