# Лабораторна робота 6 — Деплой на PaaS

**10 балів** · бонусні завдання +6

## Мета

Розгорнути образи з Лаб. 5 у два середовища, staging і prod, з базою й кешем поза
платформою. Налаштувати конвеєр так, щоб у prod потрапляв рівно той образ, що пройшов
staging, а схема бази змінювалася окремим кроком до розгортання.

Робота не про те, «щоб відкрилося в браузері», а про те, щоб розгортання було
повторюваним, відкат — передбачуваним, а дані — відновлюваними.

## Проєкт

Ті самі `wishlist-api` і `wishlist-ui`, ті самі команди й репозиторії, ті самі образи
в GHCR з Лаб. 5.

Еталонна платформа — Render. Інша PaaS допускається, якщо вона без платіжної картки
розгортає готовий образ з GHCR. Вимоги тоді ті самі, а відмінності опишіть у `DEPLOY.md`.

База — Neon, кеш — Upstash. Вбудовані бази PaaS не використовуються.

> Безкоштовні сервіси Render засинають після 15 хвилин без запитів. Перший запит
> після паузи може тривати десятки секунд — це холодний старт, а не помилка.

## Завдання

### 1. Сервіси даних (1 бал)

- Neon: окремий проєкт для кожного середовища, наприклад `wishlist-staging` і
  `wishlist-prod`.
- Upstash: окрема база Redis для кожного середовища.
- З'єднання лише через TLS: `sslmode=require` для Postgres, `rediss://` для Redis.
  Якщо конфігурація api цього не дозволяє, допрацюйте її.
- Облікові дані — лише в налаштуваннях платформи й секретах GitHub. У репозиторії,
  образі й логах конвеєра їх немає.

### 2. Міграції, які будують схему з нуля (2 бали)

У `wishlist-api` є Alembic і дві міграції. Перевірте, чи можна з них отримати робочу
схему на порожній базі.

- Запустіть `alembic upgrade head` на порожній базі й зафіксуйте, що сталося.
- Виправте історію міграцій так, щоб `upgrade head` на порожній базі давав повну схему.
- Приберіть створення таблиць при старті застосунку: схему змінюють лише міграції.
- Адресу бази міграції беруть з тих самих змінних середовища, що й застосунок, а не
  з `alembic.ini`.
- Поясніть, як привести до тієї самої історії базу, де таблиці вже є (локальну з
  Лаб. 5), не втративши даних.

<summary>Підказка</summary>

Порівняйте вміст першої міграції з моделями й подумайте, на якій базі її могли
автогенерувати. Для бази, де таблиці вже є, подивіться на `alembic stamp`.

**Доказ:** вивід `alembic upgrade head` на порожній базі й список таблиць після нього.

### 3. API у двох середовищах (1 бал)

- Два сервіси, staging і prod, з одного образу GHCR за sha-тегом.
- Уся конфігурація через змінні середовища. У кожного середовища своя база, свій кеш,
  свій секретний ключ і `ALLOWED_ORIGINS` з адресою UI саме цього середовища.
- Перевірка стану на `/health`. Вона проходить, коли недоступний лише Redis: кеш не
  є критичною залежністю.
- Застосунок слухає `0.0.0.0` і порт, який очікує платформа.

### 4. UI у двох середовищах (1 бал)

Адреса API в кожного середовища своя, а `VITE_API_BASE` вшивається під час збірки.
Оберіть один із варіантів:

- **Один образ для обох середовищ.** Адреса API підставляється під час запуску
  контейнера, а не під час збірки.
- **Окрема збірка на середовище.** Конвеєр збирає два образи UI з різним
  `VITE_API_BASE`.
- **Статичний хостинг.** UI розгортається як статичний сайт, без nginx-образу з Лаб. 5.

Незалежно від варіанта оновлення сторінки на будь-якому маршруті застосунку не дає 404.

У `DEPLOY.md` поясніть, чому обрали саме цей варіант і чим за нього заплатили. Для
другого й третього — чому те, що працює в prod, не є тим, що перевіряли на staging,
і чим це ризиковано.

<details>
<summary>Підказка до першого варіанта</summary>

Офіційний образ nginx перед стартом підставляє змінні середовища в шаблони з
`/etc/nginx/templates/`. Так можна згенерувати не лише конфігурацію nginx, а й змусити
його слухати порт, який очікує платформа.

</details>

### 5. Конвеєр доставки (3 бали)

- GitHub environments `staging` і `production`, секрети — на рівні середовища.
- Push у `main`: міграція staging-бази, потім розгортання staging. Якщо міграція
  впала, розгортання не починається.
- Prod розгортається з того самого sha, що й staging, і лише після схвалення іншого
  учасника команди. Схвалити власний запуск не можна. Порядок той самий: міграція,
  потім розгортання.
- Міграція виконується окремим кроком: job у конвеєрі або, з обґрунтуванням, при
  старті контейнера. На безкоштовному тарифі Render pre-deploy command недоступний.
  У `DEPLOY.md` назвіть недолік обраного способу, який ви свідомо прийняли.
- Відкат prod — ручним запуском з sha попереднього образу. Схему при відкаті не
  чіпають.

<details>
<summary>Підказка</summary>

Deploy hook Render приймає параметр `imgURL` — адресу образу, який треба розгорнути.
Міграцію можна запустити тим самим образом, що й застосунок, лише з іншою командою.

</details>

**Доказ:** історія запусків, де видно staging → схвалення → prod з однаковим sha,
і один проведений відкат.

### 6. Експлуатаційні перевірки (2 бали)

- **Відновлення.** Зробіть логічну копію prod-бази й відновіть її в окрему базу:
  гілку Neon або локальний контейнер. Покажіть кількість рядків і найсвіжіший запис
  у ключових таблицях, порівняйте з prod. Заміряйте, скільки тривало відновлення.
- **Без кешу.** На staging зробіть Redis недоступним, наприклад неправильним паролем.
  Покажіть, що API відповідає, перевірка стану проходить, а сервіс не
  перезапускається. Потім поверніть як було.
- **Бюджет з'єднань.** Порахуйте, скільки з'єднань api може одночасно відкрити до бази
  (воркери × пул × копії), і порівняйте з лімітом свого тарифу Neon.

Усе — у `DEPLOY.md`, з командами й цифрами.

<details>
<summary>Підказка</summary>

`pg_dump` має бути тієї самої або новішої основної версії, що й сервер. Якщо
встановлена локально старіша, запустіть його з образу `postgres` потрібної версії.

</details>

## Бонусні завдання (+6)

- **Один образ UI (+1)** — за перший варіант у завданні 4.
- **Зміна схеми без простою (+2).** Перейменування або видалення колонки на prod за
  кілька релізів (expand/contract), з доказом, що на кожному кроці працює відкат на
  один реліз назад.
- **Окремі ролі бази (+1).** Міграції виконуються від власника таблиць, застосунок
  працює з правами лише на дані.
- **Smoke-тест (+1).** Після розгортання staging конвеєр перевіряє ключові ендпоінти;
  якщо перевірка не пройшла, prod не запускається.
- **Пулер (+1).** Застосунок підключається до Neon через пулер, міграції — напряму.
  Поясніть, чому саме так.
