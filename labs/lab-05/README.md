# Лабораторна робота 5 — Контейнеризація

**10 балів** · бонусні завдання +6

## Мета

Запакувати обидва застосунки в образи, підняти весь стек однією командою і навчити
конвеєр збирати й публікувати образи. Робота не про те, «щоб запустилося», а про те,
щоб образ був відтворюваним, без секретів усередині, а за його тегом було видно, що
це за образ і з якого коду.

Наступна робота деплоїть на PaaS саме ці образи з реєстру, тому тут вони мають
опинитися в GHCR.

## Проєкт

Ті самі `wishlist-api` і `wishlist-ui`, ті самі команди, ті самі репозиторії з
конвеєрами й ruleset'ами з Лаб. 4.

Як розкласти нові файли — вирішуєте самі: `compose.yaml` можна покласти в один із
репозиторіїв або в окремий командний. Головне — щоб інструкція запуску працювала.

Якщо в репозиторії вже є Dockerfile чи compose — вимоги стосуються того, що лежить у
вас у результаті. Можна переписати з нуля, можна виправити наявне.

## Що здається

**Командні репозиторії:**

- `Dockerfile` і `.dockerignore` — в обох застосунках
- `compose.yaml` і `.env.example` — там, де вирішить команда
- `.github/workflows/ci.yml` — розширений конвеєр з Лаб. 4
- `docs/containers.md` — таблиця розмірів (завдання 2), доказ роботи тому
  (завдання 3), скріншот пакета (завдання 4), діагностика (завдання 5)

**Особисте портфоліо** — `lab-05/README.md` у вашому `devops-portfolio`:

- посилання на командні репозиторії
- **ваш внесок** — кілька речень: що саме ви зробили, з посиланнями на свої pull
  request'и
- інструкція запуску стеку — від клону до робочого застосунку

Використання AI-асистентів дозволене. Але ви маєте розуміти і пояснити кожен рядок
Dockerfile, compose і конвеєра.

## Спільні вимоги

Перевіряються в кожному завданні окремо.

| Вимога | Що це означає |
|---|---|
| Закріплені версії | Базові образи й образи в compose — з конкретним тегом (`python:3.12-slim`, `postgres:16-alpine`). Жодного `latest`, жодного образу без тегу |
| Жодного секрету в образі | `.env`, паролі й токени не потрапляють ні в образ, ні в репозиторій. Паролі не передають через `ARG` — вони лишаються в історії образу |
| Порядок шарів | Те, що змінюється рідко, — раніше. Зміна одного файлу коду не перевстановлює залежності |
| Exec-форма | `CMD` / `ENTRYPOINT` — JSON-масивом, щоб головним процесом був застосунок, а не shell |
| Зрозумілі імена | Job збірки образу читабельна у списку перевірок pull request'а |

### Як перевірятиметься

```
docker run --rm <image> whoami      # not root
docker run --rm <image> ls -a       # no .env, .git, tests
```

Змініть один рядок коду й перезберіть: крок встановлення залежностей має бути взятий
з кешу (`CACHED` у виводі збірки).

`docker stop` має зупиняти контейнер за секунду-дві, а не через 10 секунд.

</details>

`compose.yaml`, який піднімає Postgres, Redis, API і UI.

| Що | Вимога |
|---|---|

### Доказ, що том працює

У `docs/containers.md` — вивід команд: створіть запис через UI чи API, виконайте
`docker compose down` і `docker compose up -d` — запис на місці. Потім
`docker compose down -v` і `up -d` — одним реченням поясніть, що змінилося і чому.

### Інструкція запуску

Шлях від клону до робочого стеку: копіювання `.env.example`, які значення заповнити,
одна команда запуску. UI має отримувати дані від API.

**Перевірятиметься запуском, а не читанням.**

<details>
<summary><b>Завдання 5. Діагностика</b> — 1 бал</summary>

<br>

Один учасник команди свідомо ламає стек, інший шукає проблему, не знаючи, що саме
зламано. Варіанти поломки: застосунок слухає `127.0.0.1`, неправильний порт у
`ports`, неправильне ім'я хоста бази.

Той, хто шукає, проходить чеклист з лекції «Сервіс піднявся, але недоступний». У
`docs/containers.md` — що було зламано, на якому кроці чеклиста це знайшли, якою
командою і її вивід.

</details>

## Підказки

- Зазирнути всередину образу: `docker run --rm -it <image> sh`
- `docker compose config` показує файл з підставленими змінними й ловить помилки до
  запуску
- Браузер звертається до API з вашої машини, тому для UI адреса API —
  `http://localhost:<порт>`, а не `http://api:8000`. І ця адреса походження UI має
  бути в дозволених для CORS
- Імена образів у GHCR — лише в нижньому регістрі; `docker/metadata-action` враховує це
  сам
- Образи й кеш збірки швидко займають диск: `docker system df` покаже, скільки саме
- Документація: [Dockerfile](https://docs.docker.com/reference/dockerfile/) ·
  [Compose](https://docs.docker.com/reference/compose-file/) ·
  [build-push-action](https://github.com/docker/build-push-action) ·
  [metadata-action](https://github.com/docker/metadata-action)
