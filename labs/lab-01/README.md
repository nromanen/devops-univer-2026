# Лабораторна робота 1 — Середовище та професійний Git workflow

**5 балів** · бонусне завдання +2

## Мета

Підготувати робоче середовище й налаштувати репозиторій так, щоб у нього неможливо було внести зміни в обхід процесу. Усі наступні роботи курсу лягають у цей репозиторій.

## Що здається

Публічний репозиторій `devops-portfolio` з такою структурою:

```
devops-portfolio/
├── README.md              # портфоліо
├── .gitignore
├── LICENSE
├── .editorconfig
├── .github/
│   └── pull_request_template.md
├── lab-01/
│   ├── README.md          # звіт по цій роботі
│   └── assets/            # скріншоти
├── lab-02/ … lab-10/
└── final/
```

**Усі письмові відповіді** з цієї роботи — в одному файлі `lab-01/README.md`. Окремих звітів заводити не треба.

Репозиторій **обов'язково публічний**: на безкоштовному плані GitHub правила захисту гілок працюють лише в публічних репозиторіях.

<br>

### Глобальні параметри Git

Задати й пояснити письмово:

| Параметр | Що вказати |
|---|---|
| `user.name`, `user.email` | Пошта має збігатися з підтвердженою поштою GitHub-акаунта — інакше коміти не прив'яжуться до профілю |
| `init.defaultBranch` | `main` |
| `core.autocrlf` | Значення залежить від ОС |
| `pull.rebase` | `true` |
| `core.editor` | Редактор для повідомлень комітів |

**Письмово:** чому значення `core.autocrlf` різне для Windows і Unix і що станеться в команді зі змішаними системами, якщо його не задати. Чим історія з `pull.rebase=true` відрізняється від типової.

**Перевірка:** вивід `git config --list --global` у звіті.

### Редактор

Налаштувати VS Code або інший редактор (JetBrains, Neovim) для роботи з інфраструктурним кодом. Потрібні розширення для:

- історії змін і авторства рядків просто в редакторі
- підсвічування та перевірки Dockerfile і Compose-файлів
- YAML **із перевіркою за схемою** — редактор має підсвічувати помилку в конфігурації GitHub Actions ще до коміту
- перегляду Markdown

### `.editorconfig`

Створити файл із правилами відступів, кінців рядків і фінального переносу. Увімкнути форматування при збереженні.

> **Увага:** VS Code не читає `.editorconfig` без окремого розширення. Без нього файл лежить у репозиторії й не діє. Перевірте, що правила справді застосовуються.

**Перевірка:** скріншот у `lab-01/assets/`, де редактор підсвічує навмисно зламаний YAML.

<details>
<summary><b>Завдання 3. GitHub і доступ</b> — 1 бал</summary>

<br>

- Акаунт із заповненим профілем: ім'я, фото, короткий опис. Профіль — частина вашого портфоліо, його бачитимуть роботодавці.
- Увімкнена двофакторна автентифікація.
- SSH-ключ типу `ed25519` **із парольною фразою**. Публічна частина додається в акаунт.
- Перевірка з'єднання: `ssh -T git@github.com`, вивід у звіті.

**Письмово:** чому приватний ключ ніколи не потрапляє в репозиторій і що робити, якщо він усе ж туди потрапив. Другу частину продумайте як послідовність дій, а не одним реченням.

</details>

<details>
<summary><b>Завдання 5. Правила репозиторію</b> — 1 бал</summary>

<br>

Налаштувати ruleset для гілки `main`. У персональному репозиторії працюють ті правила, які не потребують другої людини:

| Правило | Навіщо |
|---|---|
| Обов'язковий pull request перед злиттям | Зміна проходить через явний етап, а не летить прямо в `main` |
| Заборона force-push | Історію основної гілки не можна переписати |
| Заборона видалення гілки | Захист від випадковості |
| Лінійна історія | Тримає `git log` читабельним |

**Чого поки не вмикаємо і чому:**

- **Обов'язкові перевірки статусу** — їх немає в списку, поки конвеєр жодного разу не запускався. Список формується з імен завдань, які система вже бачила. Це завдання з'явиться в Лаб. 4.
- **Обов'язкова рецензія й заборона обходу правил** — у персональному репозиторії ви заблокуєте самі себе: автор pull request не може його схвалити. Це вмикається в Лаб. 2, коли з'явиться команда.

**Письмово:** що саме зміниться в налаштуваннях, коли робота стане командною, і чому «заборона обходу правил адміністратором» безпечна в команді й шкідлива соло.

### Дошка проєкту

Project із колонками Backlog / In Progress / Review / Done. Задача на кожен модуль курсу і на фінальний проєкт. Увімкнені вбудовані автоматизації:

- нова задача → Backlog
- відкритий PR → Review
- злитий PR → Done
- закрита задача → Done

### Шаблон pull request

`.github/pull_request_template.md`: опис змін, посилання на задачу, чек-лист самоперевірки, спосіб перевірки результату.

Відтворити всі налаштування репозиторію не через веб-інтерфейс, а програмно — через API GitHub або консольний клієнт `gh`.

**Вимоги:**

- конфігурація зберігається у файлі в репозиторії, а не існує лише як історія команд
- скрипт застосовує її до **нового порожнього репозиторію** однією командою
- продемонструвати це на тестовому репозиторії, який потім можна видалити

**Письмово:** чому налаштування, зроблені кліками, — проблема для команди, і що змінюється, коли вони описані кодом. Це та сама ідея, яку в курсі побачите ще двічі: у конвеєрі та в описі інфраструктури.

## Як здається

1. Робота ведеться у власній гілці, зливається в `main` **через pull request**. Прямий пуш у `main` — робота не зарахована незалежно від вмісту.
2. Робота вважається зданою після усної перевірки, на якій ви пояснюєте прийняті рішення.
3. AI-асистенти дозволені. Але «так порадив AI» не є відповіддю на питання «чому саме так»: ви маєте пояснити рішення, назвати альтернативи й сказати, за яких умов воно було б неправильним.
