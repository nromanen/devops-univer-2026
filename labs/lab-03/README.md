## Мета

Написати три інструменти автоматизації, якими ви користуватиметеся далі в курсі. Робота не про алгоритми — вона про те, як виглядає інструмент, придатний до експлуатації: з довідкою, зрозумілими кодами виходу, журналом і документацією.

## Що здається

Тека `lab-03/` у вашому репозиторії `devops-portfolio`:

```
lab-03/
├── README.md          # опис інструментів і приклади запуску
├── backup.sh
├── api_monitor.py
├── config/            # конфігурація монітора
└── hooks/             # git-хуки
```

Зміни потрапляють у `main` **через pull request** із власної гілки. Прямий пуш — робота не зарахована.

## Спільні вимоги до всіх інструментів

Ці вимоги перевіряються в кожному завданні окремо.

| Вимога | Що це означає |
|---|---|
| Довідка | `--help` виводить призначення, усі параметри й приклад запуску |
| Коди виходу | `0` — успіх, ненульовий — помилка. Різні причини — різні коди |
| Перевірка параметрів | Немає обов'язкового параметра або файл не існує — зрозуміле повідомлення, а не трасування стека |
| Журналювання | Кожен запуск лишає запис: час, дія, результат |
| Документація | У `README.md` теки: що робить, як запустити, приклад виводу |

Для bash обов'язково `set -euo pipefail` на початку. У README поясніть **своїми словами**, що робить кожен із трьох прапорців і що зламається без них.

<details>
<summary><b>Завдання 1. Скрипт резервного копіювання</b> — 3 бали</summary>

<br>

Скрипт `backup.sh` створює стиснений архів указаної теки й зберігає лише задану кількість останніх копій.

### Параметри

| Параметр | Обов'язковий | Призначення |
|---|---|---|
| `--source <шлях>` | так | Тека, яку архівуємо |
| `--dest <шлях>` | так | Куди складати архіви |
| `--keep <N>` | ні, типово 5 | Скільки останніх копій зберігати |
| `--dry-run` | ні | Показати, що було б зроблено, нічого не змінюючи |
| `--help` | — | Довідка |

### Поведінка

1. Перевірити, що тека-джерело існує й доступна для читання. Немає — вихід із кодом помилки і зрозумілим повідомленням.
2. Перевірити, що тека призначення існує; якщо ні — створити.
3. Створити архів `tar.gz` з іменем, що містить **ім'я джерела й часову мітку**, наприклад `project-2026-09-01-143022.tar.gz`. Мітка має забезпечувати правильне сортування за іменем.
4. Порахувати наявні архіви цього джерела в теці призначення. Якщо їх більше за `--keep` — видалити найстаріші, лишивши рівно `N`.
5. Записати в журнал результат: скільки заархівовано, скільки видалено, розмір архіву.

### Вимоги до реалізації

- Ротація рахує **лише архіви цього джерела**. Якщо в теці лежать чужі файли, вони не мають зникнути.
- `--dry-run` не створює й не видаляє нічого, але друкує повний перелік дій.
- Шляхи з пробілами мають працювати.

### Як перевіряється

- Запуск шість разів поспіль із `--keep 3` — у теці лишається рівно три найновіші архіви.
- Запуск із неіснуючим джерелом — ненульовий код виходу і повідомлення без трасування.
- `--dry-run` після п'яти запусків — друкує, що буде видалено, і не видаляє.

</details>

<details>
<summary><b>Завдання 2. Монітор доступності API</b> — 4 бали</summary>

<br>

Скрипт `api_monitor.py` перевіряє список endpoint'ів і повідомляє про проблеми. Головна вимога: він має **розрізняти типи збою**, а не писати «сервіс недоступний» на все.

### Конфігурація

Список цілей у файлі (YAML або JSON, на ваш вибір). Для кожної цілі: адреса, очікуваний код відповіді, тайм-аут, поріг часу відповіді. Приклад структури наведіть у README.

Адреси й секрети — не в коді. Адреса вебхука для сповіщень береться зі змінної середовища.

### Типи збою

Кожен випадок обробляється окремо й дає **своє** повідомлення в журналі:

| Тип | Коли виникає |
|---|---|
| DNS | Ім'я не резолвиться |
| З'єднання відхилено | Сервер відповів, але на цьому порту ніхто не слухає |
| Тайм-аут | Відповіді немає у відведений час |
| Помилка сертифіката | З'єднання встановлюється, але сертифікат не приймається |
| Несподіваний код | Сервіс відповів, але не тим кодом, якого очікували |
| Повільна відповідь | Код правильний, але час перевищив поріг |

Це прямо пов'язано з лекцією 3: типи збою відповідають етапам, на яких запит зупиняється.

### Поведінка

1. Перевірити всі цілі зі списку.
2. При мережевій помилці — одна повторна спроба перед тим, як визнати збій.
3. Зберегти результати перевірки у структурований файл: час, ціль, статус, час відповіді, тип збою якщо був.
4. Надіслати сповіщення у месенджер (Slack, Discord або Telegram — на вибір) для кожної проблемної цілі. У повідомленні має бути видно **тип збою**, а не лише факт.
5. Код виходу: `0` якщо всі цілі здорові, ненульовий якщо є проблеми.

### Як перевіряється

Прогін по списку, що містить щонайменше чотири завідомо різні випадки: неіснуючий домен, закритий порт на доступному сервері, домен із простроченим сертифікатом, робочий endpoint із несподіваним кодом. У журналі мають бути **чотири різні повідомлення**.

Публічні тестові домени для сертифікатів існують — знайдіть їх самостійно.

### Письмово в README

Чим «з'єднання відхилено» відрізняється від «тайм-аут» і чому в реальному інциденті ці два випадки ведуть до різних дій.

</details>

<details>
<summary><b>Завдання 3. Інтеграція з Git</b> — 1 бал</summary>

<br>

Два хуки в теці `hooks/` разом з інструкцією встановлення.

### Хук перед комітом

Запускає лінтер **лише на файлах, які потрапляють у коміт**, а не на всьому репозиторії. Знайдено проблеми — коміт не створюється.

Для bash-скриптів підійде `shellcheck`, для Python — будь-який лінтер на ваш вибір.

### Хук перед відправкою

Запускає тести. Тести не проходять — відправка не відбувається.

### Встановлення

Хуки не потрапляють у репозиторій автоматично — тека `.git/hooks` не версіонується. У README опишіть, як їх встановити: копіюванням, символічним посиланням або через налаштування `core.hooksPath`.

### Письмово в README

Чому хуки **не є** засобом контролю: вони живуть на машині розробника й обходяться одним прапорцем. Що саме роблять обов'язкові перевірки в конвеєрі, чого хуки зробити не можуть.

</details>

## Бонусні завдання

<details>
<summary><b>Бонус 1. Скрипт моніторингу системи</b> — +2 бали</summary>

<br>

Скрипт `monitor.sh` перевіряє стан машини й сигналить при перевищенні порогів.

**Показники:** використання процесора, пам'яті, вільне місце на дисках, стан заданих сервісів або процесів.

**Пороги** задаються змінними середовища або конфігураційним файлом — не хардкодяться в скрипті.

**Поведінка:** при перевищенні порога — запис у журнал і ненульовий код виходу. Вивід придатний для запуску за розкладом: без інтерактивних елементів, кожен рядок самодостатній.

**Як перевіряється:** штучно занизити поріг до значення, яке точно перевищено, і показати спрацювання.

**Додатково:** налаштувати запуск за розкладом через `cron` і показати записи в журналі за кілька запусків.

</details>

<details>
<summary><b>Бонус 2. Аналізатор журналів веб-сервера</b> — +2 бали</summary>

<br>

Скрипт `log_analyzer.py` розбирає журнал у комбінованому форматі й будує звіт.

**Результати:** топ-N адрес за кількістю запитів, розподіл кодів відповіді за класами, години пікового навантаження.

**Параметри:** вхідний файл, вихідний файл, формат виводу (текст або структурований), кількість позицій у топі.

**Стійкість:** пошкоджені рядки не мають валити скрипт. Їх рахують окремо й повідомляють кількість у звіті.

**Обов'язково:** щонайменше один автоматичний тест на функцію розбору одного рядка — включно з випадком некоректного рядка.

**Де взяти дані:** зразки журналів веб-серверів є у відкритому доступі, або згенеруйте власний.

</details>

<details>
<summary><b>Бонус 3. Утиліта на компільованій мові</b> — +2 бали</summary>

<br>

Консольна утиліта на Go, яка розкладає файли теки за типами (документи, зображення, відео, архіви).

**Вимоги:** підкоманди й розбір прапорців, режим `--dry-run`, збірка в статичний виконуваний файл.

**Письмово:** порівняйте розмір виконуваного файла й час запуску зі скриптовим аналогом. Поясніть, у яких випадках компільована утиліта виправдана, а в яких скрипт зручніший.

</details>
