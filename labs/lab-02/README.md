# Лабораторна робота 2 — Командна робота з Git

**6 балів** · бонусне завдання +1

## Мета

Відпрацювати командний процес: рецензування, конфлікти злиття, правила, які працюють тільки тоді, коли людей більше однієї. У Лаб. 1 половину таких правил увімкнути було неможливо — тут вони нарешті мають сенс.

## Що здається

Спільний публічний репозиторій команди `team-devops-handbook`:

```
team-devops-handbook/
├── README.md              # склад команди, призначення довідника
├── .github/
│   └── CODEOWNERS
├── docs/
│   ├── branching.md       # конвенції гілок і комітів
│   ├── editor-config.md   # спільні налаштування
│   ├── readme-template.md
│   ├── code-review.md     # чек-лист рецензування
│   └── conflict.md        # розбір конфлікту з завдання 4
└── assets/                # скріншоти
```

Робота оцінюється **індивідуально**, але через спільний репозиторій: видно, хто що зробив, хто як рецензував.

<details>
<summary><b>Завдання 1. Команда й правила репозиторію</b> — 1 бал</summary>

<br>

Команди по 2–3 студенти. Один учасник створює публічний репозиторій, решта додаються як collaborators.

### Ruleset для `main`

| Правило | Значення |
|---|---|
| Обов'язковий pull request | увімкнено |
| Кількість схвалень | 2, або 1 якщо в команді двоє |
| Скидання застарілих схвалень при нових комітах | увімкнено |
| Обов'язкова рецензія від власників коду | увімкнено |
| Заборона force-push і видалення гілки | увімкнено |
| **Заборона обходу правил адміністратором** | **увімкнено** |

Останній пункт — головна відмінність від Лаб. 1. Соло він блокував вас самих; у команді завжди є хто схвалить, тому правило стає справжнім, а не декоративним.

### CODEOWNERS

Файл `.github/CODEOWNERS`, що зіставляє шляхи з учасниками: у кожного розділу довідника свій власник. Рецензентів після цього призначає система, а не людська пам'ять.

**Перевірка:** скріншот налаштувань ruleset у `assets/` і склад команди в README.

</details>

<details>
<summary><b>Завдання 2. Спільний довідник</b> — 1 бал</summary>

<br>

Команда веде технічний довідник — це і є предмет роботи. Застосунок не пишеться: предметом навмисно є текстові та конфігураційні файли, з якими ви працюватимете далі в курсі.

Розділи в `docs/`, **по одному відповідальному на розділ**:

| Розділ | Зміст |
|---|---|
| Конвенції гілок і комітів | Як називати гілки, як формулювати повідомлення, що робити з робочими комітами перед злиттям |
| Спільні налаштування | `.editorconfig` і `.gitignore` для проєктів курсу, з поясненням кожного значення |
| Шаблон README | Заготовка для нового проєкту: які розділи обов'язкові й чому |
| Чек-лист рецензування | На що дивитися в чужому pull request — конкретні пункти, не «перевірити якість» |

Розділи мають бути придатними до використання: наприкінці семестру ви маєте змогти взяти звідси `.editorconfig` і покласти в новий проєкт без правок.

</details>

<details>
<summary><b>Завдання 3. Процес pull request</b> — 1 бал</summary>

<br>

Кожен учасник працює у власній гілці `feature/<ім'я>-<тема>`. На кожну зміну — окремий pull request.

### Вимоги до рецензії

- щонайменше **одне змістовне зауваження по суті**; «виглядає добре» без зауважень не рахується
- автор вносить правки **окремим комітом** у ту саму гілку, не переписуючи історію поверх уже прорецензованого
- обговорення закривається автором тільки після того, як зауваження враховано або аргументовано відхилено

### Що вважається змістовним зауваженням

Те, що стосується суті: незрозуміле формулювання, суперечність із іншим розділом, пропущений випадок, неточність у команді. Зауваження про кому чи пробіл — робота форматера, не людини.

**Перевірка:** посилання на 3–4 злиті pull request із видимими коментарями рецензентів. Кожен учасник має бути й автором, і рецензентом.

</details>

<details>
<summary><b>Завдання 4. Конфлікт злиття</b> — 1 бал</summary>

<br>

Двоє учасників одночасно змінюють **один і той самий ключ** у спільному конфігураційному файлі (`.editorconfig` підходить ідеально) і обидва відкривають pull request. Перший зливається без проблем, другий отримує конфлікт.

### Що треба показати

Два способи вирішення того самого конфлікту:

1. **Помилковий** — такий, після якого файл лишається **синтаксично коректним**, але поведінка змінилася: узяті обидві половини, загублений ключ, збережене не те значення.
2. **Правильний** — з поясненням, чому саме він правильний.

Суть завдання: показати, що конфлікт у структурованій конфігурації небезпечніший за конфлікт у тексті. У тексті помилка видна очима; у конфігурації файл виглядає нормально, а система поводиться інакше.

**Оформлення:** `docs/conflict.md` — обидва варіанти вирішення та їх наслідки. Пишіть коротко: суть у демонстрації, не в обсязі тексту.

</details>

<details>
<summary><b>Завдання 5. Історія і хук</b> — 1 бал</summary>

<br>

### Чиста історія

Перед злиттям звести робочі коміти гілки в один зі змістовним повідомленням. Спосіб на ваш вибір: squash при злитті або інтерактивне перебазування локально.

**Перевірка:** `git log --oneline` основної гілки після кількох злитих pull request. У ньому не має бути комітів на кшталт `fix`, `fix2`, `try again`, `wip`.

**Письмово в довіднику:** який спосіб обрала команда й чому. Це рішення, а не дрібниця: воно визначає, як виглядатиме історія проєкту через рік.

### Хук перед комітом

Локальний хук, що перевіряє формат повідомлення коміту або відсутність зайвих пробілів у кінці рядків. Опишіть у довіднику, як його встановити — тека `.git/hooks` не версіонується, тому хук не приїде з клоном сам.

</details>

<details>
<summary><b>Завдання 6. Локальне ім'я і remote</b> — 1 бал</summary>

<br>

Коротка вправа, яка знімає поширену хибну уяву.

1. Перейменувати локальну теку клону.
2. Перевірити `git remote -v`.
3. Зробити push.

**Письмово:** чому ім'я локальної теки й ім'я віддаленого репозиторію не пов'язані, і в який єдиний момент вони збігаються.

</details>

<details>
<summary><b>Бонус. Конвенції комітів</b> — +1 бал</summary>

<br>

Запровадити в команді єдиний формат повідомлень комітів із автоматичною перевіркою.

**Вимоги:**

- формат описаний у довіднику з прикладами правильних і неправильних повідомлень
- перевірка автоматична, а не на совісті автора
- за історією автоматично генерується список змін

**Письмово:** що дає формалізований формат повідомлень, крім охайності, і в якому місці курсу це знадобиться далі.

</details>

---

## Як здається

1. Кожен учасник вносить зміни **лише через pull request** із власної гілки.
2. Робота вважається зданою після усної перевірки, на якій кожен учасник пояснює свій внесок і рішення команди.
3. AI-асистенти дозволені. Але «так порадив AI» не є відповіддю на питання «чому саме так».

Оцінюється індивідуально.

| Критерій | Бали |

| Якість рецензування чужих pull request | 1 |

| Вправа з перейменуванням і письмове пояснення | 1 |
