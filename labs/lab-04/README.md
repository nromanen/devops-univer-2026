# Лабораторна робота 4 — Безперервна інтеграція

**10 балів** · бонусні завдання +6

## Мета

Узяти чужий проєкт, запустити його локально й побудувати для нього конвеєр, який не
дає злити зламаний код. Робота не про написання застосунку — вона про те, як
перевірки стають обов'язковими, а не добровільними.

У Лаб. 1 ми відклали обов'язкові перевірки статусу: їх немає в списку, поки конвеєр
жодного разу не запускався. Тепер він запуститься.

Цей проєкт супроводжуватиме вас до кінця курсу: далі ви його контейнеризуєте,
задеплоїте на PaaS і накриєте моніторингом. Конвеєр, який ви зараз напишете,
нарощуватиметься в наступних роботах.

## Проєкт

Команди по 2–3 студенти. Два репозиторії:

| Репозиторій | Стек |
|---|---|
| `wishlist-api` | Python, FastAPI, SQLAlchemy, Postgres, Redis |
| `wishlist-ui` | Vue 3, Vite, TypeScript, ESLint, Tailwind |

Один учасник робить **fork обох репозиторіїв**, решта додаються як collaborators.
Форки лишаються публічними — на безкоштовному плані правила захисту гілок працюють
лише в публічних репозиторіях.

Як розподілити роботу всередині команди — вирішуєте самі. Оцінка в усіх учасників
однакова.

## Що здається

**Командні форки** — уся технічна частина:

```
wishlist-api/                     wishlist-ui/
├── .github/workflows/ci.yml      ├── .github/workflows/ci.yml
├── tests/                        └── docs/
└── docs/                             ├── checks.md
    ├── checks.md                     └── assets/
    └── assets/
```

- `ci.yml` — конвеєр
- `docs/checks.md` — скріншоти з завдання 4 і таблиця з завдання 5
- `docs/assets/` — самі скріншоти

**Особисте портфоліо** — `lab-04/README.md` у вашому `devops-portfolio`:

- посилання на обидва командні форки
- **ваш внесок** — кілька речень у вільній формі: що саме ви зробили, у якому
  репозиторії, з посиланнями на свої pull request'и. Пишіть так, ніби це читає
  стороння людина, яка не знає ні проєкту, ні курсу
- інструкція локального запуску (завдання 1) — у кожного своя, бо запускає кожен сам

Використання AI-асистентів дозволене. Але ви маєте розуміти і пояснити, що робить
кожен рядок вашого конвеєра.

## Спільні вимоги до обох конвеєрів

Перевіряються в кожному завданні окремо.

| Вимога | Що це означає |
|---|---|
| Закріплені версії | `runs-on` із конкретною версією ОС, усі `uses` із явною версією. Жодного `latest`, жодної гілки замість мітки |
| Порядок перевірок | Найдешевше — найраніше. Лінтер не має чекати на тести |
| Кеш залежностей | Повторний прогін без зміни залежностей не завантажує їх із мережі заново |
| Зрозумілі імена | Ім'я job'а має бути читабельним у списку перевірок pull request'а: з нього видно, що саме впало |
| Тригери | Конвеєр запускається на pull request і на push у `main`. Не на кожну подію підряд |

<summary><b>Завдання 1. Запустити локально</b> — 2 бали</summary>

<br>

**Виконує кожен учасник окремо.** Поки людина не підняла проєкт руками, вона не знає,
що саме має робити конвеєр.

Підніміть обидва застосунки: Postgres, Redis, API, UI. Переконайтеся, що UI справді
отримує дані від API, а не показує порожні заглушки.

| Що | Вимога |
|---|---|
| Postgres і Redis | У контейнерах або локально — на ваш розсуд |
| Змінні середовища | Зібрані в `.env.example`, без справжніх значень |
| API | Відповідає на `/docs`, хоча б один ендпоінт повертає дані з бази |
| UI | Відкривається й виконує запит до API |

### Інструкція відтворення

У `lab-04/README.md` — шлях від клону до робочого застосунку з конкретними командами.
Той, хто її читає, не має нічого додумувати.

**Перевірятиметься запуском, а не читанням.**

</details>

<details>
<summary><b>Завдання 2. Конвеєр для API</b> — 3 бали</summary>

<br>

Файл `.github/workflows/ci.yml` у форку `wishlist-api`.

| Крок | Вимога |
|---|---|
| Бази | Postgres і Redis як сервіси job'а, **з перевіркою готовності** |
| Залежності | Встановлення відтворюване, з кешем |
| Стиль | `ruff` або `flake8`, конфігурація лежить у репозиторії |
| Тести | `pytest` |

Тести не повинні стартувати, доки база не приймає з'єднання. Без перевірки готовності
конвеєр падатиме через раз — і це буде саме той нестабільний тест, про який ішлося на
лекції.

### Про тести

Якщо тестів у проєкті немає або їх замало — напишіть **мінімум два**:

- перевірка health-ендпоінта, яка не торкається бази
- перевірка ендпоінта, який **справді читає або пише в Postgres**

Другий обов'язковий: без нього сервіси в конвеєрі не потрібні взагалі, і ви не
дізнаєтеся, чи правильно їх підключили.

</details>

<summary><b>Завдання 3. Конвеєр для UI</b> — 2 бали</summary>

<br>

Файл `.github/workflows/ci.yml` у форку `wishlist-ui`.

| Крок | Вимога |
|---|---|
| Залежності | Команда для відтворюваного встановлення, не `npm install` |
| Стиль | `npm run lint` |
| Типи | `vue-tsc` |
| Збірка | `npm run build`, результат зберігається артефактом |

Скрипта `test` у проєкті немає — дописувати тести не треба, це тема іншого курсу.
Ваш конвеєр для UI перевіряє стиль, типи й те, що проєкт узагалі збирається.

</details>

<details>
<summary><b>Завдання 4. Зробити перевірки обов'язковими</b> — 2 бали</summary>

<br>

Конвеєр, який можна проігнорувати, — це порада, а не правило. Налаштуйте ruleset для
`main` **в обох форках**:

| Правило | Значення |
|---|---|
| Обов'язковий pull request | увімкнено |
| **Обов'язкові перевірки статусу** | **імена job'ів з ваших конвеєрів** |
| Гілка актуальна щодо `main` перед злиттям | увімкнено |
| Скидання застарілих схвалень при нових комітах | увімкнено |
| Заборона force-push і видалення гілки | увімкнено |
| Заборона обходу правил адміністратором | увімкнено |

Імена перевірок з'являються в списку лише після того, як конвеєр відпрацював хоча б
раз — саме тому це завдання йде після двох попередніх, а не перед ними.

### Доказ

Відкрийте pull request зі **свідомо зламаним** кодом: порушення стилю або падаючий
тест. У `docs/checks.md` кожного форка — три скріншоти з підписами:

1. Pull request із червоною перевіркою і **заблокованою** кнопкою злиття
2. Журнал прогону з конкретним рядком помилки
3. Той самий pull request після виправлення: зелено, кнопка активна

Три скріншоти, не більше.

</details>

<summary><b>Завдання 5. Виміряти ефект кешу</b> — 1 бал</summary>

<br>

У `docs/checks.md` кожного форка — таблиця:

| Прогін | Час |
|---|---|
| Без кешу | |
| З кешем | |

«Без кешу» — перший прогін або прогін після зміни файлу залежностей. «З кешем» —
наступний за ним. Час беріть зі сторінки прогону.

Під таблицею одним рядком: який крок виявився найдовшим.

## Підказки

- Сервіси job'а описуються ключем `services`; з кроків вони доступні як `localhost` на
  зазначеному порту
- `setup-python` і `setup-node` вміють кешувати самі — окремий `actions/cache` для
  залежностей зазвичай не потрібен
- Рядок підключення до бази в конвеєрі задається змінною середовища, а не правкою коду
- Документація: [GitHub Actions](https://docs.github.com/en/actions) ·
  [сервіси в job](https://docs.github.com/en/actions/using-containerized-services/about-service-containers)
